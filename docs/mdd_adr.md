# ADR: решение по Metrics Driven Development для времени отклика сервиса инференса

## Статус
Принято

## Контекст

Я проектирую ML-систему для прогнозирования риска дефицита товара на складе.  
В этой системе сервис инференса используется в оперативном контуре принятия решений, поэтому время отклика является критически важной технической метрикой.

В рамках задания мне предоставлены два набора данных по времени отклика:
- **существующая система**;
- **улучшенная система**.

По визуализации видно, что распределение времени отклика улучшенной системы смещено влево относительно существующей, то есть ответы приходят быстрее. Однако для принятия архитектурного решения я опираюсь не на визуальное впечатление, а на статистическую проверку гипотез.

---

## Решение

### Проверяемая гипотеза

Я формулирую гипотезы так:

- **H0:** среднее время отклика улучшенной системы не меньше среднего времени отклика существующей системы.
- **H1:** среднее время отклика улучшенной системы меньше среднего времени отклика существующей системы.

### Уровень значимости

Я выбираю уровень значимости:

`alpha = 0.05`

### Выбранный тест

Для сравнения двух независимых выборок я использую **односторонний двухвыборочный t-тест Уэлча**.

Я считаю этот тест уместным, потому что:
- сравниваются две независимые выборки;
- объем выборок очень большой;
- меня интересует направленное улучшение — снижение среднего времени отклика;
- тест Уэлча не требует предположения о равенстве дисперсий.

### Результат статистической проверки

По данным задания:
- среднее время отклика существующей системы около **3.5 сек**;
- среднее время отклика улучшенной системы около **2.0 сек**;
- стандартное отклонение в обоих случаях около **0.4 сек**;
- объем выборок очень большой.

При таком масштабе различий статистический тест дает:
- `t-statistic ≈ -1875.08`
- `p-value < 0.001`

Следовательно, **нулевая гипотеза отвергается**, и я принимаю вывод о том, что улучшенная система действительно имеет меньшее среднее время отклика.

### Архитектурное решение

На основании Metrics Driven Development я принимаю решение:

1. **считать улучшенную систему целевой производственной версией сервиса инференса**;
2. **переключить основной трафик на новую версию сервиса**;
3. **сохранить предыдущую версию как вариант отката**;
4. **зафиксировать время отклика как обязательный критерий допуска перед выкладкой новых версий**.

Иначе говоря, я не просто констатирую, что новая версия быстрее, а превращаю это в архитектурное правило:

**новая версия сервиса инференса допускается к производственному трафику только при статистически подтвержденном снижении среднего времени отклика и при отсутствии ухудшения остальных SLO.**

---

## Последствия

### Положительные последствия

- сервис инференса будет лучше соответствовать SLO по времени отклика;
- система станет более пригодной для сценария реального времени;
- решения о развитии архитектуры будут приниматься на основе измерений, а не интуитивно;
- в проекте появляется воспроизводимый MDD-подход, который можно повторять для следующих релизов.

### Риски и ограничения

- снижение времени отклика само по себе не гарантирует улучшение качества модели;
- слишком агрессивная оптимизация времени отклика может ухудшить качество предсказаний;
- перед полным переключением трафика нужно дополнительно контролировать `error rate`, доступность и модельные метрики.

### Правило применения решения

Я считаю, что новая версия сервиса инференса может быть выкачена в прод только если одновременно выполняются условия:
- время отклика статистически лучше базовой версии;
- `error rate` не ухудшился;
- модельные метрики не просели ниже допустимого уровня;
- сервис проходит health-check и остается доступным.

---

## Краткий вывод

В рамках Metrics Driven Development я использовала два набора данных по времени отклика, сформулировала гипотезы **H0** и **H1**, выбрала уровень значимости **0.05**, определила статистический тест и зафиксировала результат статистической проверки. На основании этого я приняла архитектурное решение: переключать трафик на улучшенную версию сервиса инференса и использовать статистически подтвержденное улучшение времени отклика как обязательный критерий допуска новой версии в прод.
